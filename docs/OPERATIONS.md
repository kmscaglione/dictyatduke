# Operations & maintainer runbook (production)

**Who this is for:** whoever runs dictyBase after (or alongside) the current maintainer.
This is the tribal knowledge — the stuff that isn't obvious from the code and that will
otherwise live in one person's head.

**Read these first, in order:**
1. `README.md` — architecture, project layout, data pipeline, endpoints, code gotchas.
2. This file — how the real production box works, how to deploy, what breaks.
3. `docs/CURATION.md` — the curator workflow (web portal, no terminal).

`docs/deployment.md` is a **generic** "how to deploy this on any Linux VM" guide (it
describes Caddy). **Duke production does not work that way** — it is Puppet-managed httpd.
Use *this* file for production; use `deployment.md` only if standing up a fresh host
somewhere else.

---

## 1. The 60-second mental model

- One Python **stdlib** process (`serve.py`) listens on `127.0.0.1:8774`. Apache httpd
  reverse-proxies the public HTTPS site to it.
- It serves a vanilla-JS SPA (`index.html` + `app.js` + `styles.css`) and a REST API.
- **There is no database.** All data are pre-built static JSON/FASTA/GFF assets under
  `assets/`, regenerated by scripts in `scripts/`. The server just reads them.
- Therefore: **updating data = re-run a build script + redeploy the asset.** No migrations.
- **Single process, on purpose.** Sessions, rate limits, and the BLAST semaphore are
  in-memory. Do not run multiple workers — that state cannot be forked.

## 3. The production box

- **Host:** `web-dictylabs-01.oit.duke.edu` — AlmaLinux 9, Azure/Hyper-V VM,
  8 vCPU (Xeon 8462Y+), ~15 GiB RAM.
- **Disk:** `/srv` ≈ 65 GB total (LVM `VolGroup00-srv`, **extendable by OIT without a
  rebuild** — ask if you need more; the wild-isolate genome ambitions will need it).
- **Code lives at:** `/srv/web/dicty.labs.duke.edu/html`
- **Service:** systemd unit **`dicty`** → runs `serve.py` as user **`apache`** (uid 48) on
  `127.0.0.1:8774`.
- **Web layer:** Apache httpd, **Puppet-managed**. The vhost
  `25-dicty.labs.duke.edu-https.conf` is auto-generated from
  `/srv/web/dicty.labs.duke.edu/access/vhost_info.yaml`. The reverse-proxy directives were
  added by OIT and live outside that template — **do not hand-edit the vhost, Puppet will
  revert it.** Proxy changes are an OIT request.
- **SELinux is Enforcing.** The proxy only works because of
  `setsebool -P httpd_can_network_connect 1`. If the site 503s after a rebuild, check this.

### The ownership model (this trips everyone up)

OIT `web_chown`'d the whole `html/` tree to **owner `apache`, group `dicty-at-duke`,
mode `ug=rwX`**. Consequences:

- You **can write** existing files (via the group). Editing `news_manual.json`, running a
  build script that overwrites `assets/*.json` — all fine.
- You **cannot `chmod`** them (you're not the owner). `chmod` will error
  `Operation not permitted`. **That error is harmless noise — skip the chmod.**
- For **new** directories you create that Apache must read or write, hand them over the
  Duke way:
  ```bash
  sudo /srv/web/bin/web_chown apache <dir>     # usage: web_chown USER DIRECTORY
  ```
  (It prompts Y for recursive; does `chown -hR apache` + `chmod -R ug=rwX`. Use this —
  **not** `chmod`.)
- **Anything `serve.py` writes must be apache-owned**: `cache/`, `uploads/`. The service
  runs as `apache` and is *not* in `dicty-at-duke`, so it can't rely on group writes.
  A missing/unwritable `cache/` is what caused the `/api/recent-papers` 502 once.

## 4. Deploying a change

**Golden rule: deploy through git. Do not hand-patch the server.** (It has drifted before
and reconciling is miserable.)

```bash
# 1. On your Mac — push to BOTH remotes.
git push origin master     # GitHub (dev/primary)
git push gitlab master     # Duke GitLab (the deploy remote; needs VPN + PAT)

# 2. On the server
cd /srv/web/dicty.labs.duke.edu/html
git fetch origin master        # NB: the SERVER's "origin" is GitLab
git reset --hard origin/master

# 3. Only if serve.py (or anything server-side) changed:
sudo systemctl restart dicty
```

**Notes and gotchas:**
- **`git reset --hard` is SAFE here.** The ~1 GB of genome data, BLAST DBs, `cache/`, and
  `uploads/` are all **gitignored** — the reset only touches tracked files.
- **Type the PAT, don't paste it.** The terminal mangles pastes with bracketed-paste
  artifacts (`00~`/`01~`) and the push fails with a confusing auth error. Plain
  `git push gitlab master` with the interactive prompt is the reliable path.
- **Remotes are named differently in each place.** Mac: `origin`=GitHub, `gitlab`=GitLab.
  Server: `origin`=GitLab. Read carefully before you fetch.
- **GitHub can get ahead of you.** The monthly GitHub Action `refresh-external.yml`
  auto-commits refreshed data **to GitHub only**. `git pull --rebase` before pushing, or
  you'll conflict.

## 5. When do I need to restart?

| Changed | Restart needed? |
|---|---|
| `app.js`, `index.html`, `styles.css` | **No** — served fresh from disk. |
| `assets/*.json` (data rebuild) | **No** — read per request. (Asset version stamp auto-busts caches.) |
| `serve.py` (endpoints, headers, config) | **Yes** — `sudo systemctl restart dicty`. |
| Newly added genome files | **Yes** — `serve.py` caches genome state at startup (`genome_seq()` caches even an *empty* result), so `/api/sequence` will 404 until you restart. |
| `/etc/dicty.env` (e.g. curator password) | **Yes**. |

## 6. Refreshing data

Everything under `assets/` is reproducible. Re-run the relevant script, commit, deploy.

```bash
python3 scripts/build_data.py            # gene_index, phenotypes, downloads_manifest, corpus merge
python3 scripts/build_data.py --go       # also re-downloads the GO GAF -> go_annotations.json
python3 scripts/build_stock_center.py    # full Dicty Stock Center catalog from dictyBase GraphQL
python3 scripts/build_stock_center.py plasmids
python3 scripts/build_gene_facets.py     # advanced-finder facets (needs ortholog_disease + rnaseq)
```

- `build_data.py` also runs `build_gene_facets.py` at the end (skips gracefully if inputs
  are missing).
- **Stock center**: pulls from the live dictyBase GraphQL API
  (`https://graphql.dictybase.dev/graphql`). It is **flaky and 502s a lot** — the script
  retries and paginates politely. `totalCount` from that API is unreliable (it returns the
  batch size). Text fields come HTML-entity-encoded and must be unescaped (`_u()` handles
  it).
- **Curator edits are protected.** Stock edits live in `assets/stock_overrides.json` and
  are merged over the base catalog at serve time; the edit handler stamps `edited_date` so
  a re-fetch won't clobber them. **Never "fix" this by writing edits into
  `stock_center.json` directly.**

### Genome data (not in git — must be rebuilt on a fresh host)

```bash
pip install --user pysam                      # BUILD-time only, not a runtime dep
python3 scripts/fetch_genomes.py              # 9 core assemblies (incl. AX4)
python3 scripts/fetch_paper_genomes.py        # the additional paper/isolate assemblies
python3 scripts/build_blastdb.py              # per-species BLAST DBs
python3 scripts/build_browser_tracks.py       # bgzip+tabix GFFs for IGV byte-range
sudo /srv/web/bin/web_chown apache assets/genomes
sudo systemctl restart dicty                  # REQUIRED (see §5)
```
BLAST+ is installed system-wide by OIT at `/usr/bin/{makeblastdb,blastn,tblastn}`;
`serve.py` and `build_blastdb.py` both find it via `shutil.which`.

## 7. Gotchas that will bite you

- **Adding a `/tools/X` route requires THREE edits in `app.js`**, not one:
  1. the `openTool()` dispatch,
  2. the `hydrateFromRoute()` tool whitelist (direct loads / refresh),
  3. the `toolLink` click-interceptor whitelist (in-app navigation).
  Miss #2 and the page works in-app but 404s on refresh. Miss #3 and it full-page-reloads.
- **Never gzip the genome files.** `.fna/.fai/.gff/.gtf` are deliberately excluded from
  `COMPRESSIBLE_EXTS`, and gzip is skipped on **ranged** requests. IGV reads these by byte
  offset — compress them and the genome browser breaks in a way that looks random.
- **Single process only.** Sessions, rate limiting, and the BLAST semaphore are in-memory.
  Adding workers silently breaks curator logins.
- **HTTP keep-alive is OFF** (`serve.py` speaks HTTP/1.0). Real browsers are fine (Apache
  handles keep-alive). But `ab -k` against `serve.py` directly will *hang* — benchmark
  without `-k`. This is not a bug.
- **`BLAST_MAX_CONCURRENT=6`** is set via a systemd drop-in
  `/etc/systemd/system/dicty.service.d/override.conf` (`sudo systemctl edit dicty`). The
  main unit is OIT-written and minimal. **If Puppet ever purges the drop-in directory,
  BLAST silently reverts to the default 3.** Worth checking if BLAST feels slow.
- **`chmod` errors on site files are expected** (you're not the owner) — use `web_chown`.
- The **IGV browser takes ~10–15 s to appear** on first open (it fetches igv.org →
  S3 genome list → genome → tracks). Transient "Loading…" is not a failure.

## 8. Troubleshooting

| Symptom | Likely cause |
|---|---|
| Site 503s | Reverse proxy / SELinux — check `setsebool -P httpd_can_network_connect 1`; check `systemctl status dicty`. |
| Deep links 404, home page fine | The proxy isn't routing to `serve.py` (Puppet vhost regenerated?) — OIT. |
| `/api/sequence` 404s, BLAST says not installed | Genome data missing, or added without a restart (§5). |
| `/api/recent-papers` 502 | `cache/` missing or not apache-writable → `mkdir -p cache && sudo /srv/web/bin/web_chown apache cache`. |
| Curator can't log in | `CURATOR_PASSWORD` not set in `/etc/dicty.env`, or service not restarted after setting it. Sessions are in-memory — a restart logs everyone out (expected). |
| Genome browser broken/garbled | Something started gzipping the genome files, or the tabix `.tbi` is missing. |
| Stale data on the site | Asset version stamp didn't bump — confirm the rebuilt JSON actually landed and mtime changed. |

## 9. Design decisions — please don't undo these

These look like limitations. They are choices, and they're why the thing costs ~$700/year
and one part-time person instead of a cluster and a team.

1. **No database.** Data are reproducible static assets. This removes an entire class of
   ops burden (backups, migrations, tuning, an always-on daemon). The tradeoff — data are
   snapshots refreshed by scripts — is deliberate and correct for a read-mostly resource.
2. **Standard library only, no build step.** Any Python 3 runs it. No npm, no bundler, no
   dependency rot. A successor can read the whole stack.
3. **Single process.** See above. Capacity is ~1,850 req/s on dynamic gene endpoints —
   far beyond this community's traffic.
4. **Scope was cut on purpose.** Ordering is email/mailto, not an order service. No user
   accounts. These are what let the backend stay small; adding them re-creates the heavy
   system this replaced.
5. **Versioned-immutable assets.** `serve.py` injects `window.__ASSET_V`; a fetch wrapper
   appends `?v=` to `/assets/*.json`. A data rebuild bumps the stamp → new URL → auto-fresh.
   **No CDN purge is ever needed.** Don't "simplify" this away.

## 10. Onboarding a second maintainer (the bus-factor fix)

The architecture is cheap to run but currently depends on one person's knowledge. To fix
that, a second person should:

1. Read `README.md`, then this file.
2. Get: Duke VPN, `dicty-at-duke` group membership, server SSH, a GitLab PAT, GitHub access.
3. **Do a trivial deploy end-to-end** (fix a typo → push both remotes → fetch/reset on the
   server → verify). This one exercise teaches most of §4.
4. **Re-run a data build** (`build_stock_center.py`) and deploy the asset.
5. **Restart the service** once, on purpose, so it isn't scary.
6. Walk the curator flow in `docs/CURATION.md` end-to-end.

Anyone who can do those six things can keep the site alive indefinitely. That — not the
architecture — is what makes this durable.
